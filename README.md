# 别再为「告警推到哪」折腾了

一份个人开发者的接收端选型笔记：三条常见路线各自卡在哪，我们最后怎么绕开的，以及四个可以照抄的真实案例。

不是框架，不是 SDK，就是一套跑起来过的做法。

---

## 起因

手上有一堆东西需要往外推：

- 某个开源仓库有没有新提交
- 自己的小服务是不是还活着
- 一台免费云主机是不是被平台回收了

要的东西很简单：**有人替我把消息送到手机上。**

然后我发现，难的不是监控，是**接收端**。监控逻辑一晚上能写完，找一个能长期稳定收消息的地方，能耗掉一星期。

下面是我踩过的三条弯路，和最后走通的那条直路。

---

## 三条弯路，一条直路

### 路线一：QQ 机器人（最容易起步，最容易死）

个人 QQ 号挂协议跑机器人，是很多人入门的第一站。填个回调地址，机器人在线，消息就来了。

问题在于**它不受官方保护**：

- 个人号跑协议属于非官方客户端，风控重点照顾对象
- 轻则限制登录，重则直接封号，封了历史消息全丢
- 你觉得跑得好好的，第二天起来号没了，监控链路跟着断

**结论：临时验证可以，长期依赖不行。**

### 路线二：企业微信「接收消息服务器」回调（看着正规，实际门槛极高）

企业微信有官方的应用消息回调，文档也写得很规整。但真要接通，得逐条过下面这些关：

| 门槛 | 具体是什么 |
|---|---|
| 必须 HTTPS | 死活不能用 http，得配证书 |
| 域名要求 | 需要**企业可信域名**，或备案主体与企业主体同名的域名 |
| 域名归属校验 | 要在一个固定路径下放一个校验文件，能访问到才算通过 |
| 消息加密 | 支持 AES 加密，涉及 Token 和 EncodingAESKey 两个值 |
| 响应时限 | 5 秒内必须回应，超时会被重试 |
| 首次配置 | 需要原样回显一个校验串，验证服务器身份 |

官方原话是：URL 回调模式需要企业可信域名和 IP（或备案主体与企业同名的域名）。

**对个人开发者来说，卡点通常就在「备案」和「域名归属」这两步**——不是技术难，是资质难。域名备案要主体、要时间、要材料，很多人到这里就放弃了。

### 路线三：企业微信智能机器人「长连接」

这是后来才有的路子，我觉得是这三条里最适合个人的。

创建机器人**时把连接方式选成「使用长连接」**，拿到两个值：

```
Bot ID
Secret
```

然后用官方 SDK 主动连上去就行。它和路线二的根本区别是**方向反过来**：

```
路线二：平台 → 你的服务器（需要公网 IP、域名、备案）
路线三：你的程序 → 平台       （不需要公网，不需要域名）
```

不需要公网 IP，不需要域名，不需要 Nginx，不需要备案。

代价是：**没有「填个链接就完事」的简单**。你得自己保活、自己重连、自己处理消息类型，还得区分「长连接专用的 Secret」和「URL 回调那套 Token / EncodingAESKey」——这两套值不通用，填错了就是连不上，报错也不告诉你为什么。

### 路线四：企业微信群里加个机器人（我们实际用的这条）

前面三条，一条会被封，两条太麻烦。而这件事其实还有第四种解法，简单到有点不真实：

**在企业微信群里，加一个群机器人。**

群设置 → 群机器人 → 添加 → 拿到一个 Webhook 地址。然后 POST 一段 JSON：

```bash
curl '你自己的群机器人Webhook地址' \
  -H 'Content-Type: application/json' \
  -d '{"msgtype":"text","text":{"content":"服务挂了"}}'
```

不需要注册应用，不需要审核，不需要公网 IP，不需要域名，不需要备案，不需要保活。

**它跟「智能机器人」是两回事。** 它就是一个群成员，消息发出去群里所有人都能看到，手机上直接弹通知。没有 Bot ID，没有 Secret，没有连接要维持。

限制也得说清楚：

| 限制 | 具体 |
|---|---|
| 只能往群里发 | 不能私聊，不能收取消息 |
| 发送节奏 | 平台本身不卡你发多少条。但我们在自己的发送端加了一层节流，纯粹是防程序抽风把群刷爆 |
| 消息类型有限 | 文本、markdown、图片、文件、模板卡片 |
| URL 就是密码 | 谁拿到谁能往你群里发，泄露了要立刻移除重建 |

如果诉求只是「有事通知我一声」，这四条限制一条都不影响。**单向推送，正好就是我们要的全部。**

## 四条路对比

| | QQ 机器人 | 企微 URL 回调 | 企微长连接 | **企微群机器人** |
|---|---|---|---|---|
| 上手成本 | 低 | 高（卡资质） | 中高 | **最低** |
| 需要公网 IP | 不需要 | **需要** | 不需要 | **不需要** |
| 需要域名 | 不需要 | **需要，且要过归属校验** | 不需要 | **不需要** |
| 需要备案 | 不需要 | **通常需要** | 不需要 | **不需要** |
| 要维持连接 | 要 | 不要 | **要，还得自己重连** | **不要** |
| 稳定性 | 差（随时封号） | 好 | 好 | **好** |
| 能收消息 | 能 | 能 | 能 | **不能** |
| 适合谁 | 临时测试 | 有企业资质 | 需要双向通信 | **只想收通知** |

如果你有备案域名和企业资质，路线二最省心，平台帮你兜底。

如果你需要「用户在群里问、机器人答」，那是路线三。

如果你只想要「有事通知我」，**路线四，五分钟接完**。

---

## 我们最后的选择：群机器人 Webhook，一条路走到底

长连接我们也认真看过，最后的结论是：**对我们没必要。**

我们的场景全是单向推送——服务挂了、仓库更新了、机器被平台回收了。没有一条需要让平台把消息推回来。

所以整条链路压缩成一句话：

```
任何事件 → 一个 HTTP POST → 群机器人 Webhook → 群里弹通知
```

不需要长连接，不需要保活，不需要重连，不需要 Bot ID 和 Secret。

**代价是放弃双向能力。** 哪天真需要「@ 机器人它就回应」，再回去看路线三。在那之前，多一行配置都是浪费。

## 四个可以照抄的案例

这四个都是我们自己真在跑的，代码在 `examples/` 里，密钥全部走环境变量。

> 案例三（云主机保活）的完整脚本因涉及具体云平台的接口对接与验签细节，已移到私有仓库 `cloudbox-keeper`，本仓库只保留架构说明。

### 案例一：GitHub 仓库更新 → 企微

**场景**：盯一个开源项目，它一提交我就想知道。

**做法**：不轮询 API（有速率限制），直接读仓库的 `commits.atom` 订阅源，比对最新一条的 sha。

```
拉 commits.atom → 取第一条的 sha → 和上次存的比
  ├─ 一样 → 什么都不做（避免刷屏）
  └─ 不一样 → 推一条，附 commit 链接，更新存储
```

**关键点**：只在 sha 变化时推。这一步决定了它是「有用的通知」还是「垃圾短信」。

**两个坑，都踩过：**

1. **分支名别写死 `main`。** 很多老仓库的默认分支叫 `master`，写错就是直接 404，而 404 不会告诉你是仓库名错了还是分支名错了。代码里默认走「仓库默认分支」，别自己猜。
2. **atom 里的 `<id>` 不是裸 sha。** 它长这样：`tag:github.com,2008:Grit::Commit/<40位hex>`。直接拿 `<id>` 当 sha 用，比对结果永远是「不同」，于是每次检查都推一条重复消息。必须用正则从里面把 40 位 hex 抽出来。

**频率**：别太勤。这类仓库一个月可能才提交一次，**十天检查一次足够**，也省额度。

### 案例二：站点/服务存活 → 企微

**场景**：自己的小服务跑在免费平台上，随时可能睡死或挂掉。

**做法**：定时发一个 HTTP 请求，看重不重得回来。

```
每 N 分钟请求一次
  ├─ 2xx → 记一笔正常
  └─ 超时 / 5xx / 连不上 → 推告警，附状态码和耗时
```

**关键点**：**状态变化才推**，不要每次都推。挂了推一次，恢复了也推一次，中间不刷屏。

### 案例三：免费云主机保活（8 小时限制 + 看门狗 + 外部拉起）

这个是四个里最折腾的，也是最有意思的。

**场景**：用一台免费云主机跑长任务。平台规则是：空闲一段时间自动回收，单次运行有上限（我们这台被调整成 **8 小时**），到点就关机。

任务本身不能中断，机器却会被收走。

**做法**：三层结构，各管一段。

```
┌─────────────────────────────────────────────┐
│ 第一层：云主机上的看门狗                      │
│  每 5 分钟向外 ping 一次「门铃」              │
│  同时检查任务进程是否还活着，死了就拉起来      │
└──────────────────┬──────────────────────────┘
                   │ 定时 ping
                   ▼
┌─────────────────────────────────────────────┐
│ 第二层：一台永不关机的「门铃」服务            │
│  免费 PaaS（我们用自己的 Render 实例）        │
│  收到 ping 就回 200，顺便记录最后一次心跳时间  │
│  它自己也怕睡，所以需要一个外部定时器叫醒它    │
└──────────────────┬──────────────────────────┘
                   │ 收到平台的回收事件 webhook
                   ▼
┌─────────────────────────────────────────────┐
│ 第三层：开机动作                              │
│  平台判定实例被回收 → 发 webhook 到门铃       │
│  门铃验证签名后，调云平台 API 把机器开起来     │
└─────────────────────────────────────────────┘
```

三个要点：

1. **看门狗不负责重启机器，它只负责「敲铃」**。机器死了，敲铃的人也没了，所以必须有外部视角。
2. **门铃本身也会睡**（免费 PaaS 十几分钟无访问就休眠），所以要有一个外部定时器定期叫醒它，否则它连自己都保不住。
3. **开机动作要幂等**。同一个回收事件可能重复投递，重复开机不能报错。

自动恢复链路还需要写进系统的开机自启里：机器重启 → 拉起守护进程 → 判断任务是否在跑 → 没跑就续上（我们用的是会话文件断点续跑，不是从头再来）。

> 完整实现（`autostart.sh` / `watchdog.sh` / `keeper.py`）不在这个公开仓库里，已移走；下面所说的结构可以照着自己的平台搭。

**这个案例的价值不在于「绕过限制」**，而在于：任何「会被回收的环境 + 不能中断的任务」，都需要这套外部视角的保活结构。同理适用于 CI runner、临时容器、Spot 实例。

### 案例四：任意 Webhook → 企微（转发器）

**场景**：第三方服务（支付、构建、告警平台）给你发 webhook，你不知道它发了什么，也不知道格式对不对。

**做法**：自己架一个极简的转发端点。

```
POST /alert
  body: {"event": "...", "source": "...", "detail": "..."}
  → 校验 → 格式化 → 推企微 → 立刻回 200
```

**两个坑写在这里免得你踩**：

1. **必须立刻回 200，不要等推送完成再回。** 有的服务 5 秒不回应就判失败并重试，而推送本身可能就要几秒。
2. **严格校验 body 结构。** 我们遇到过格式不对时端点直接挂住不回包，请求方干等 15 秒超时。宁可回 400，也别不回。

## 快速开始

### 第一步：拿到一个能收消息的地方

企业微信群里 → 群设置 → 群机器人 → 添加 → 复制 Webhook 地址。

就这一步。没有第二步。

### 第二步：跑起来

```bash
git clone <this-repo>
cd alert-receiver-guide
cp examples/.env.example examples/.env
# 填进你自己的地址和密钥
pip install -r examples/requirements.txt
python examples/wecom_group_bot.py
```

### 第三步：确认真的通了

别信「代码没报错」。发一条测试消息，**去手机上看到它**，才算通。

## 关于安全

这个仓库里**没有任何真实凭证**。所有地址写成「你自己的 xxx」，所有密钥写成占位符。

你自己往里填的时候，遵守三条：

1. **密钥不要进 git**。用 `.env`，并且 `.gitignore` 掉。
2. **群机器人 Webhook URL 就是密码**。任何拿到这个 URL 的人都能往你的群发消息，泄露了立刻在群里移除重建。
3. **公开仓库前扫一遍**。`ghp_`、`sk-`、`webhook/send?key=`、`whsec_`、`cfk_` 这些前缀，用正则搜一遍再 push。宁可多扫一次。
